# ebpf-observability-gap

**보안 로그가 비어 있을 때, 정말 아무 일도 없었던 걸까요, 아니면 수집기가 못 본 걸까요?**

Falco / Tetragon 로그에서 "조용했던 구간"과 "관측되지 않은 구간"을 구분하는 분석기와, 그걸 확인한 실험 기록입니다.

## 문제: 0과 "데이터 없음"은 다르다

Prometheus로 알림을 만들어 본 적이 있다면 익숙한 문제입니다. 에러 수가 **0**인 것과 에러 메트릭이 **아예 안 들어오는 것**은 다르고, 그래서 `absent()` 알림을 따로 둡니다.

보안 로그도 같습니다. eBPF 기반 보안 수집기(Falco, Tetragon)는 커널에서 프로세스 실행, 파일 열기 같은 이벤트를 받아 로그로 남깁니다. 그런데 로그에 아무것도 없는 5분이 있다면:

- 정말 **아무 일도 없었을** 수도 있고,
- 수집기가 **죽었거나**, 이벤트가 몰려 **버퍼에서 버려졌거나(드롭)**, 남긴 로그가 **회전되며 지워졌을** 수도 있습니다.

침해 사고를 조사할 때 "그 시간엔 기록이 없다"는 결론이 아니라 질문입니다. 이 프로젝트는 그 질문에 답하려고 만들었습니다.

<details>
<summary>용어 정리 (보안·커널 쪽이 낯선 분들께)</summary>

| 용어 | 뜻 |
|---|---|
| eBPF | 커널에 작은 프로그램을 붙여 시스템 호출 같은 이벤트를 안전하게 관찰하는 리눅스 기능 |
| Falco | eBPF로 시스템 호출을 보고, 규칙(예: "민감한 파일 읽기")에 걸리면 알림을 남기는 오픈소스 보안 도구 |
| Tetragon | eBPF로 프로세스 실행·종료 같은 이벤트를 전부 기록하는 오픈소스 보안 관측 도구 |
| 링버퍼 / 드롭 | 커널이 이벤트를 넘기는 고정 크기 버퍼. 수집기가 못 따라가면 가득 차서 이벤트를 버린다 |
| 하트비트 | "나 살아 있고, 지금까지 이만큼 받았다"를 주기적으로 남기는 기록 |

</details>

## 결론 먼저

1. **로그만 봐서는 구분할 수 없습니다.** 하지만 수집기가 자기 상태를 같이 남기면(하트비트, 카운터) 대부분 기계적으로 구분됩니다.
2. **증거로 판정하는 규칙만으로 틀린 답이 없었습니다.** 손으로 정답을 매긴 35개 구간에서 30개를 맞히고 5개는 판단을 보류했고, 무작위로 넣은 장애 96개 구간은 모두 맞혔습니다.
3. **증거가 없는 구간을 LLM에게 맡겨 봤지만 믿을 만하지 않았습니다.** 실행마다 답이 바뀌었고, 여러 번 물어 투표해도 일관되게 틀리는 건 고쳐지지 않았습니다. 판단을 바꾼 건 더 똑똑한 추론이 아니라 **더 많은 증거**였습니다.

## 한눈에 보기

Falco 두 대(node-a, node-b)를 띄우고 node-a만 두 번 멈춘 실험입니다. 10초마다 한 칸입니다.

```
█ 관측  · 조용  ~ 지연  X 유실(확정)  ? 유실(추정)

[node-a/falco]  █████~~~█████XXX·████
  [DELAYED] 09:17:20–09:17:50  하트비트 44초 끊김, 커널 카운터 연속 (+897건), 드롭 0
  [LOST   ] 09:18:40–09:19:10  수집기 재시작 (프로세스 시작 시각 변경) · 신호 공백 41.2초

[node-b/falco]  █████████████████████
```

두 공백은 로그만 보면 똑같이 "40초간 아무것도 없음"입니다. 하지만

- 첫 번째(`docker pause`)는 커널이 이벤트를 계속 쌓아 두었다가 재개 후 처리했습니다 → **관측됨, 늦게 처리됨**
- 두 번째(컨테이너 삭제)는 수집기가 없어서 아무도 기록하지 않았습니다 → **관측 안 됨**

이 차이는 수집기가 5초마다 남긴 하트비트의 두 숫자(프로세스 시작 시각, 커널 이벤트 카운터)로 가려집니다.

## 어떻게 구분하나: 증거 다섯 가지

| 증거 | 무엇을 비교하나 | 잡아내는 것 | 실험에서 본 예 |
|---|---|---|---|
| **드롭 카운터** | 수집기가 스스로 센 "버린 이벤트 수" | 버퍼가 넘친 구간 | Falco를 CPU 5%로 묶자 5초에 수십만 건 드롭 |
| **하트비트** | 끊긴 앞뒤의 프로세스 시작 시각, 커널 이벤트 카운터 | 재시작(`LOST`) vs 일시 정지(`DELAYED`) | 위 "한눈에 보기" |
| **저장 단계 대조** | "내보냈다"고 센 이벤트 수 vs 로그에 실제로 남은 줄 수 | 로그 회전·용량 제한으로 지워진 구간 | 6만 3천 건을 내보냈는데 로그에는 1,862건 |
| **교차 확인** | 같은 호스트의 다른 수집기가 그 시각 본 것 | 한쪽 수집기만 죽은 구간 | Tetragon이 꺼진 동안 Falco는 워크로드를 계속 봄 |
| **워크로드 리듬** (증거가 없을 때) | 주기적으로 도는 프로세스가 끊겼는지 | 추정만 가능 → `SUSP` | 워크로드가 멈춘 건지 수집기가 멈춘 건지 모름 |

위의 네 가지는 모두 **"수집기에게 스스로를 증언하게 하는"** 방법입니다. 운영에서 쓰는 하트비트·dead man's switch(Alertmanager의 `Watchdog` 알림 같은) 패턴을 보안 로그에 적용한 셈입니다.

판정 결과는 다섯 상태 중 하나입니다.

| 상태 | 뜻 |
|---|---|
| `OBS` █ | 관측됨 |
| `QUIET` · | 관측됨, 조용했음 (수집기는 살아 있었음) |
| `DELAYED` ~ | 관측됨, 늦게 처리됨 |
| `LOST` X | 관측 안 됨 (증거로 확정) |
| `SUSP` ? | 관측 안 됨으로 추정 (증거 없음) → 판단 보류, 또는 `--llm` |

자세한 판정 순서는 [docs/reference.md](docs/reference.md#동작-방식)에 있습니다.

## LLM에게 맡겨 보니

처음 구상은 "긴 로그 맥락을 LLM이 보고 판단"이었습니다. 그래서 규칙이 판단을 보류한 5개 구간을 OpenAI `gpt-5.5`에게 여러 번 물었습니다.

| 구간 | 정답 | 한 번씩 4회 | 5번 물어 투표 |
|---|---|---|---|
| 합성: 드롭 신호 없는 전체 블랙아웃 | 관측 안 됨 | ✓✓✓✓ | ✓ |
| 합성: healthcheck만 사라진 부분 유실 | 관측 안 됨 | ✗✗✗✗ | ✗ |
| Tetragon: 막 켜졌고 워크로드 시작 전 | 관측됨 | ✓✓✓✓ | ✓ |
| Tetragon: 워크로드를 멈춘 조용한 40초 | 관측됨 | ✗✗✓✓ | 보류 (답이 갈림) |
| Tetragon: 수집기 삭제 | 관측 안 됨 | ✓✓✗✓ | ✓ |

- **근거가 없는 구간에서는 답이 실행마다 바뀌었습니다.** "워크로드 중지"와 "수집기 중지"는 로그상 똑같아서, 몇 번은 둘 다 한쪽으로 찍었습니다.
- **여러 번 물어 투표하면 흔들림은 "모르겠다"로 바뀝니다.** 틀린 답을 자신 있게 내는 것보다 낫습니다.
- **하지만 일관되게 틀리는 건 투표로 고쳐지지 않습니다.** 원인을 프롬프트의 한 문장으로 의심해 빼 봤지만 그대로 틀렸고, 오히려 다른 구간이 나빠져서 되돌렸습니다.
- 규칙보다 확실히 나았던 건 5개 중 1개("막 켜졌고 워크로드 시작 전")뿐이었습니다. 하트비트가 있었다면 "수집기는 살아 있고 조용함"으로 규칙이 가렸을 상황입니다.

전체 기록과 프롬프트 실험은 [docs/experiments.md](docs/experiments.md#llm-판단)에 있습니다.

## 실수에서 배운 것

해석을 한 번씩 틀렸고, 그때마다 원인을 끝까지 확인했습니다.

- **"커널이 조용히 버렸다"고 생각한 이벤트는 로그 회전으로 지워진 것이었습니다.** Tetragon 기본값(10MB × 백업 5개)은 초당 1만 건이 넘으면 몇 초치만 남깁니다. 이 발견이 [저장 단계 대조](docs/experiments.md#7-로그-회전-유실-realvmrotationsh)로 이어졌습니다.
- **일정하게 도는 워크로드를 수집기의 생존 신호로 착각했습니다.** 3초마다 도는 `cat`이 멈추자 "수집기 장애"로 판정했습니다. 수집기 자신의 하트비트만 믿도록 바꿨습니다.
- **감시자의 감시자가 죽었습니다.** 정리 명령이 하트비트 스크립트만 죽였고, 멀쩡한 Tetragon을 장애로 판정했습니다. 이벤트가 계속 나오면 살아 있는 것으로 보게 고쳤습니다.
- **노트북이 잠들어 30분 실험이 2시간짜리가 됐습니다.** 깨어난 뒤 VM 시계와 호스트 시계가 어긋나 오판했습니다. 하트비트는 수집기와 같은 시계를 쓰는 곳에서 남겨야 합니다.
- **5초 하트비트를 5초 창으로 보니 5.1초 흔들림이 공백으로 보였습니다.** 평소 간격의 1.5배 이내는 공백으로 보지 않게 했습니다.
- **로그 파일을 비웠더니 앞부분이 NUL 바이트 125KB로 채워졌습니다.** Tetragon이 파일을 연 채 원래 위치에 이어 쓰기 때문입니다.

## 빠른 시작

```bash
pip install .                                   # gapfind, tetragon-heartbeat 명령 (외부 의존성 없음)
gapfind sample.jsonl                            # 합성 샘플로 바로 확인
gapfind falco.jsonl tetragon.jsonl heartbeat.jsonl --window 5 --html report.html
gapfind falco.jsonl --follow --webhook <Slack 웹훅 URL> --metrics-port 9109   # 실시간 알림 + Prometheus
```

수집기 쪽 설정은 두 가지면 됩니다.

```bash
# Falco: 5초마다 metrics 스냅숏을 로그에 남긴다 (하트비트 + 드롭 카운터 + 내보낸 알림 수)
falco -o json_output=true -o metrics.enabled=true -o metrics.interval=5s -o metrics.output_rule=true

# Tetragon: 메트릭 서버를 켜고, 같은 호스트에서 하트비트 스크립트를 돌린다
tetragon --export-filename tetragon.jsonl --metrics-server :2112
tetragon-heartbeat --node <node_name> --out heartbeat.jsonl
```

모든 옵션, LLM 판단, 알림 형식, 테스트는 [docs/reference.md](docs/reference.md)에 있습니다.

## 한계

- 모든 실험은 한 대의 Mac 위 컨테이너·VM에서 했습니다. 실제 서버나 클라우드 클러스터에서 오래 돌려 보지는 않았습니다.
- 기준값(창 크기, 주기 판정, 조용함 기준)은 이 실험들에서 정했습니다. 자동 장애 주입으로 새 장애에도 맞는지 확인했지만, 같은 환경 안에서의 확인입니다.
- 교차 확인은 두 수집기가 같은 종류의 활동을 본다고 가정합니다.
- 하트비트도 교차 확인도 없는 로그에서는 여전히 "모르겠다"가 최선의 답입니다.
